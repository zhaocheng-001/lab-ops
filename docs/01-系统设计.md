## 二、技术选型理由

### 2.1 前端：Vue 3 + Vite + Element Plus

| 候选 | 选用理由 |
|------|----------|
| Vue 3 | 组合式 API 让复杂页面的逻辑复用更直观（设备运维 4 个页面的状态机均基于 `ref/computed` 编写）；体积小、上手快，中文社区活跃。 |
| Vite | ESM 原生加载，HMR < 100ms；生产用 Rollup 打包，Tree-shaking 友好。 |
| Element Plus | Vue 3 适配最完整的组件库，Table / Form / Dialog 可直接覆盖 90% 场景；i18n 完善。 |
| Pinia | Vue 3 官方推荐，TS 友好，比 Vuex 简洁 40%。 |

### 2.2 后端：Django + DRF

| 候选 | 选用理由 |
|------|----------|
| Django | 自带 ORM / Admin / Migration / Auth，开发效率高；`django.db.models` 的聚合与 F 表达式是统计接口的关键。 |
| DRF | ViewSet + Router 让 REST 接口样板代码降到最低；分页、过滤、序列化器开箱即用。 |
| SimpleJWT | 无状态 Token，便于前后端分离；支持刷新机制。 |

### 2.3 数据库：MySQL 8.0

事务强一致（预约审批、派单状态机需要事务），分页查询性能稳定，字段类型丰富（JSON / Decimal / DateTime），运维成熟。

## 四、设备运维模块详细设计

### 4.1 数据模型

```
┌───────────────┐        ┌────────────────────┐        ┌────────────────┐
│  FaultReport  │ 1──* 1 │ MaintenanceOrder   │  1──*  │ InspectRecord  │
│  故障报修      │        │ 维修工单            │        │ 巡检记录        │
└───────┬───────┘        └─────────┬──────────┘        └────────┬───────┘
        │                          │                            │
        │ FK:device                │ FK:device                  │ FK:device
        │ FK:laboratory            │ FK:laboratory              │ FK:laboratory
        │ FK:reporter              │ FK:handler                 │ FK:inspector
        │ FK:order                 │ FK:fault                   │ FK:plan
        └──────────────────────────┴────────────────────────────┘
                                              ▲
                                              │ FK:plan
                                ┌─────────────┴───────────┐
                                │  MaintenancePlan        │
                                │  维保计划（周期性）       │
                                └─────────────────────────┘
```

### 4.2 工单状态机

```
        pending ─────┐
            │         │
            ▼         │
        processing ───┤
            │         │
            ▼         ▼
        resolved ── verified
            │
            └── cancelled
```

转换规则（详见 `apps/maintenance/views.py`）：

| 当前状态 | 允许的操作 | 触发副作用 |
|---------|-----------|-----------|
| pending → processing | 管理员"开始处理" | 写入 `started_time` |
| processing → resolved | 处理人"完成" | 设备 status: 维修中→可用；关联报修 resolved |
| resolved → verified | 管理员"验收" | 写入 `verified_time` 和 verifier |
| pending/processing → cancelled | 管理员"取消" | 设备回可用；关联报修 closed |

### 4.3 报修 → 工单的转换

学生 / 教师 `POST /maintenance/faults/` 提交报修，后端在 `FaultReportViewSet.create` 中：
1. 自动填充 `reporter` / `reporter_name` / `reporter_role`
2. 将关联 `device.status` 切到 `REPAIRING`
3. 生成业务编号 `FR-yyyyMMddHHmmss-NNN`

管理员 `POST /maintenance/faults/{id}/dispatch/` 完成派单：
1. 创建 `MaintenanceOrder`，`source=fault`
2. 回填 `fault.order` 与 `fault.status=dispatched`
3. 写入审计日志

## 五、安全设计

1. **JWT 鉴权**：所有 API 走 `Authorization: Bearer <token>`，刷新令牌分离。
3. **权限类**：基于 `User.is_sys_admin / is_lab_admin` 自定义 `IsSysAdmin / IsLabAdminOrSystemAdmin / IsMaintenanceAdmin`。
4. **数据可见范围**：`scope_queryset_by_user()` 统一裁剪，非管理员只能看到本实验室数据。
5. **操作审计**：所有写接口走 `log_operation()` 中间件，关键字段脱敏（手机号、身份证）。

## 六、性能与扩展

- **数据库**：所有外键 `db_index=True`，状态字段加复合索引 `(status, priority)`。
- **缓存**：统计页用 Django cache 30s 失效，避免高峰期打数据库。
- **异步**：通知派发使用 `transaction.on_commit` 钩子，避免提前触发。
- **水平扩展**：前端无状态，后端可通过 Gunicorn 多 worker 横向扩展。

## 七、与传统预约系统的差异

| 维度 | 传统预约系统 | 本设计 |
|------|------------|--------|
| 范围 | 预约 + 审批 | 预约 + **故障报修 + 维修 + 维保 + 巡检** |
| 设备状态 | 仅 available/booked | **+ 维修中**（由报修自动触发） |
| 数据价值 | 仅用时记录 | **完整生命周期**，支撑资产决策 |
| 用户参与度 | 被动审批 | **主动报修 + 评价 + 巡检** |
| 设备寿命 | 坏了再修 | **周期性维保** + 巡检防患 |

> 这正是"运维"二字在本设计中的核心价值 —— 让系统不止于"预约"，更成为设备全生命周期管理的工具。
